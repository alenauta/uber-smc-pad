# SDK overlay: SMC-PAD board for the JieLi AC63 SDK

Turns the vendor SDK (`ac63_bt_sdk_release_v2.4.0`) into an SMC-PAD build **without editing the pristine SDK**. Build environment setup is in [firmware/builder/](../builder/README.md).

| File | What it does |

| [apply.py](apply.py) | Makes the working copy `$SMCPAD_WORK/work/sdk-smcpad` (default `/workspace/work/sdk-smcpad`) once, then (re)generates the SMC-PAD board in `apps/spp_and_le/board/br25` from the AC636N demo board, hooks in USB-MIDI (`--no-usb-midi` skips it), the SMC-PAD hardware drivers (`--no-smcpad-hw` skips them) and the SMC-PAD BLE / Sinco / preset stack (`--no-ble-smcpad` skips it). Why `spp_and_le`: the stock image's PID is `AC636N_TRANS`, the SDK's data-transfer (`spp_and_le`) demo. It also has the BLE GATT server that the Sinco `AE40` service and BLE-MIDI need.

## USB-MIDI
The AC63 SDK has no USB-MIDI device class out of the box (only `uac_audio.h` constants and MIDI file decoding). `apply.py` copies `usb/usb_midi.[ch]` into `apps/common/device/usb/device/` and patches:
- `usb_common_def.h`, `usb_device.c`, `usb_config.c`: adds `MIDI_CLASS` (`0x40`), `TCFG_USB_SLAVE_MIDI_ENABLE`, and 128 B of endpoint DMA (`EP1 IN/OUT`, free when MSD is off).
- `descriptor.c`, `user_setup.c`: patches the device descriptor to test VID:PID `1209:0001` (so vendor `Midi Suite` / `SincoOTA` never mistake test builds for stock firmware), answers jack-name strings (`0x10..0x12`), and allows endpoint feature requests on `USB_MIDI_EP_IN/OUT`.
- `board_smcpad_cfg.h`, `app_spp_and_le.c`: enables `TCFG_PC_ENABLE` with `USB_DEVICE_CLASS_CONFIG = MIDI_CLASS`, puts USB buffers in `.bss` (`USB_MEM_NO_USE_OVERLAY_EN = 1`), disables `SLEEP_EN` while USB is brought up, and starts the USB stack from `trans_data`.

## SMC-PAD hardware
`apply.py` copies `board/smcpad_*` into the board directory, adds the three `.c` files to the board Makefile and:
- `board_smcpad_cfg.h`: turns off the demo peripherals that sit on SMC-PAD pins (UART0 debug on PC4 = mux S2, AD key on PB1 = WS2812, the SDK `spi.c` SPI1/SPI2 drivers, the AT-UART pins PC1/PC2/PA5/PA6) and defines `TCFG_SMCPAD_HW_ENABLE 1`. There is no debug UART any more; use the diagnostic SysEx instead.
- `cpu/br25/adc_api.c`: adds `adc_ext_set_value()`. `smcpad_hw.c` owns the SARADC (the SDK's `adc_scan` stays idle while `ADC_CON.EN` is set), slips a VBAT / LDOREF / DTEMP conversion in every 8 pad frames and feeds the results back, so `adc_get_value()` and the battery code keep working.
- `app_spp_and_le.c`: calls `smcpad_start()` after `usb_start()`.

As in the stock firmware, the scan ISRs (SARADC, SPI2, UART1) and the tables they read run from RAM, so flash erase/program for VM writes cannot stall them. The SDK links with LTO, which moves never-written arrays to flash and outlines `static inline` helpers. The tables therefore carry an explicit `.data` section, the header helpers are `always_inline`, and `adc_pmu_detect_en()` (flash) is replaced by a RAM copy on top of the mask-ROM `P33_CON_SET`. `test/check_ram_isr.sh` checks the result after every build.

Differences from stock, chosen on purpose: the button LEDs start off; the key-matrix SPI runs at 1 MHz (stock ≈4 MHz); pad polarity is auto-detected from the idle level; MIDI goes out on cable 0 only (stock: 0 and 1).

## BLE, Sinco config and presets
With the SMC-PAD hardware (and without `--no-ble-smcpad`), `apply.py` also:
- copies `ble/`, `sinco/`, `midi/`, `board/smcpad_store_port.[ch]` and `board/smcpad_preset.[ch]` flat into the board dir and compiles them **instead of** `trans_data/ble_trans.c`;
- sets `TCFG_USER_EDR_ENABLE 0` (BLE only, as stock) and `TCFG_SMCPAD_BLE_ENABLE 1` in `board_smcpad_cfg.h`;
- regenerates `app_config.h` from pristine with `CONFIG_BT_SM_SUPPORT_ENABLE 1` in the `CONFIG_APP_SPP_LE` block ("Just Works" pairing).

The device advertises as stock `SMC-PAD` and answers Sinco `0x11` with `SMC-PAD_000`. The low version keeps SincoOTA willing to flash stock back. Rename it with `SMCPAD_DEVICE_NAME` in [ble/ble_smcpad.h](ble/ble_smcpad.h). Midi Suite can then read and edit presets and globals over BLE or USB. Raw-flash writes, the `0x21` erase command and the type-5 mode flag are refused. Details, the GATT table and the command support matrix are in [docs/ble_config.md](../../docs/ble_config.md).

**Safe mode** ([board/smcpad_safe.c](board/smcpad_safe.c)): two boots in a row that end within 5 s (a crash loop, or switching the pad off twice by hand) make the next boot skip all SMC-PAD drivers; BLE, OTA and USB still run. `apply.py --safe-only` builds the minimal image that always boots like that. Wrap images for SincoOTA with `python3 tools/fw/make_fwsc.py update.ufw SMC-PAD_9xx.fwsc`; the flashing order is in [docs/first_flash.md](../../docs/first_flash.md).

## Build & Host Unit Tests (Linux `x86_64` or Docker)
```sh
# Run host C unit tests (ASan/UBSan)
cd firmware/sdk_overlay
gcc -Wall -Wextra -Werror -std=c11 -I test/stubs -I usb test/test_usb_midi.c -o /tmp/test_usb_midi && /tmp/test_usb_midi && rm -f /tmp/test_usb_midi
gcc -Wall -Wextra -Werror -std=c11 -I board test/test_smcpad_logic.c -o /tmp/test_smcpad && /tmp/test_smcpad && rm -f /tmp/test_smcpad
for t in sinco_proto sinco_store ble_midi; do
    gcc -Wall -Wextra -Werror -std=c11 -fsanitize=address,undefined -g -I sinco -I midi test/test_$t.c -o /tmp/t_$t && /tmp/t_$t && rm -f /tmp/t_$t
done
gcc -Wall -Wextra -Werror -std=c11 -fsanitize=address,undefined -g -I board -I sinco \
    test/test_smcpad_preset.c -o /tmp/t_preset && /tmp/t_preset && rm -f /tmp/t_preset

# Apply overlay and build firmware image (inside firmware/builder Docker container or x86_64 Linux)
cd ../..
python3 firmware/sdk_overlay/apply.py
OUT=/workspace/out/smcpad_midi KEYFILE=/workspace/keys/smcpad.key NO_TONE=1 \
    bash firmware/builder/build_ufw.sh ac636n_spp_and_le /workspace/work/sdk-smcpad
bash firmware/sdk_overlay/test/check_ram_isr.sh /workspace/work/sdk-smcpad /workspace/out/smcpad_midi
```
Compare the area table against stock in [docs/build_host.md](../../docs/build_host.md).

> [!CAUTION]
> The pins are now the SMC-PAD's ([docs/pinmap.md](../../docs/pinmap.md)), but the drivers, the BLE server and the Sinco storage have **never run on hardware**. Pad order, knob direction, pad thresholds and PB5's role are unconfirmed, and low power is not set up yet (`SLEEP_EN` off). Images built from this are still for **build and layout verification only**. Do not flash them until the recovery path is bench-tested ([docs/recovery.md](../../docs/recovery.md)).
